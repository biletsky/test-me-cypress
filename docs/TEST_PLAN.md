# Стратегія та План Тестування: VZL Test-Me E-commerce

## 1. Мета та Підхід

Створення надійного, масштабованого набору UI та API автотестів для навчального магазину `test-me.vzl.one`.

**Ключовий принцип:** Тести фіксують очікувану поведінку (Expected Behavior). Наявні в системі дефекти мають призводити до падіння тестів (Failed), ми не підлаштовуємо код під помилкову роботу застосунку.

**Що залишилось поза покриттям (Out of Scope):**

* **Навантажувальне тестування:** Перевіряється лише обробка `Soft rate limit` (429 HTTP статус) в межах функціональних сценаріїв.
* **Безпека (Security):** SQLi та інші серверні вразливості не є пріоритетом (XSS вже протестовано).
* **Кросбраузерність:** Фокус на одному рушії (Chromium/Electron у Cypress) для швидкості розробки; адаптивність покривається окремими тестами.

## 2. Пріоритети Тестування (Risk-Based Approach)

1. **P1 (Critical) — Блокери бізнесу:** Оформлення замовлення, розрахунок кошика (знижки, доставка), ізоляція середовищ, створення замовлень через API.
2. **P2 (High) — Основний функціонал:** Фільтрація та пагінація каталогу, додавання/видалення товарів з кошика, відгуки, скасування замовлень.
3. **P3 (Medium/Low) — Зручність та UI-елементи:** Порівняння товарів, UI-валідація полів.

## 3. Ризики та Мітигація

| Ризик | Вплив | Стратегія пом'якшення | 
| ----- | ----- | ----- | 
| **Перетин даних (Flaky tests)** | Високий | Увімкнена ізоляція тестів (`testIsolation`), що очищує `localStorage` перед кожним тестом. Для API створюється нове середовище через клієнт. | 
| **Rate Limiting (429 Too Many Requests)** | Середній | Механізм `Api.createWorkspace()` обробляє статус 429 та заголовок `Retry-After`. | 
| **Відсутність ідемпотентності POST запитів** | Високий | Створення UI тесту на подвійний клік при чекауті для виявлення дефекту дублювання замовлень. | 
| **Округлення та типи даних** | Середній | Всі API-запити оперують цілими числами (копійки). Використовується окремий модуль `support/money.js` для розрахунку очікуваних копійок з цін та парсингу грошей з UI. | 

## 4. Архітектура Автоматизації (Cypress JS)

**Стек:** Cypress, JavaScript.

### Структура проєкту (Шари)
```text
specs
   cypress/e2e/{api,ui}              регресія
   │
   ├── pages/        Page Objects    класи екранів, успадковують BasePage
   ├── support/api   API client      по методу на ендпоінт, повертає сиру відповідь
   ├── support/arrange               підготовка даних UI-тестів через API (token браузера)
   ├── data/         Test data       фікстури (require) + білдери тіл запитів
   └── support/money                 розрахунок сум у копійках, парсинг грошей з UI
```
*Правило залежностей: specs → pages / api / data / money. Pages не імпортують specs, api не знає про UI.*

### Патерни та їх призначення

| Патерн | Де знаходиться | Призначення |
| :--- | :--- | :--- |
| **Page Object** | `pages/*.page.js` | Локатори й дії екрана. Успадковують `BasePage` (який містить `visit`, `reload`). |
| **Service Object / API client** | `support/api.js` | Інкапсуляція запитів (напр. `Api.createQuote(token, body)`). `failOnStatusCode: false` за замовчуванням. |
| **Test Data Builder** | `data/index.js` | Генерація валідних тіл за замовчуванням; тест перевизначає лише необхідні поля (`basket`, `checkoutBody`, `line`). |
| **Розрахунок сум** | `support/money.js` | Обчислення очікуваних сум у копійках (знижки, доставка). |
| **Arrange via API** | `support/arrange.js` | Підготовка даних для UI-тестів через API для швидкості та стабільності (UI перевіряє лише свою поведінку). |
| **Data-driven tests** | `orders.cy.js`, `workspace.cy.js` | Один сценарій, багато наборів даних з окремими звітами на кожен. |

### Робота з токенами (Ізоляція)

| Рівень | Механізм реалізації |
| :--- | :--- |
| **API** | `Api.createWorkspace()` виконує `POST /api/workspaces` (з вбудованою обробкою 429). |
| **UI** | Магазин створює token сам. `testIsolation` очищує `localStorage` перед кожним тестом. Функціонал «Почати заново» перевіряється явно через `WorkspacePage.startFresh()`. |
| **UI Arrange** | `WorkspacePage.token()` читає token *поточного браузера* з `test-me:v2`, щоб налаштувати дані через API. Токен ніколи не інжектиться в браузер і не логується. |

### Стратегія локаторів
Пріоритет селекторів: `data-testid` → `id` / `data-*`-атрибути (`data-add`, `data-compare`, `data-nav`) → роль і текст. 
CSS-класи для макета й позиційні селектори свідомо ігноруються для забезпечення стабільності тестів.
